# Voxy World Gen V2 — 1.21.1 Backport Design

Date: 2026-07-31
Branch: `backport/1.21.1`

## Goal

Build Voxy World Gen V2 (upstream target: MC 1.21.6–1.21.11) against Minecraft 1.21.1
with full feature parity: background chunk generation, Voxy auto-ingest, the
server→client LOD streaming path, the debug HUD, and the Cloth config screen.

## Target platform

| Component | Upstream (1.21.11) | Backport (1.21.1) |
| --- | --- | --- |
| Minecraft | 1.21.11 | 1.21.1 |
| Fabric API | 0.141.1+1.21.11 | 0.116.6+1.21.1 |
| Fabric Loader | 0.18.3 | 0.17.2 |
| Cloth Config | 15.0.127 | 15.0.140 |
| ModMenu | 11.0.1 | 11.0.3 |
| Mappings | Mojang official | Mojang official (unchanged) |
| Java | 21 | 21 (unchanged) |

Loom stays at 1.14.10 if it resolves 1.21.1; otherwise fall back to `1.11-SNAPSHOT`,
which is proven against 1.21.1 by the local `voxy-mc_1211` Voxy checkout.

Cloth Config 15.x and ModMenu 11.x are already the 1.21/1.21.1-era lines, so those
are version bumps within a line rather than API migrations.

## Method: compile-driven, ground-truth-verified

1. Flip the build configuration to the target platform.
2. Iterate `./gradlew compileJava`, fixing type-level drift until clean.
3. Audit — by `javap` against the Loom-produced 1.21.1 Mojmap jar — everything javac
   cannot check.

Step 3 is not optional. Two classes of failure are invisible to the compiler and
surface only at runtime:

- **Mixin `@Invoker`/`@Accessor`/`@Inject` targets.** A stale name is a mixin-apply
  crash on world load. `voxyworldgenv2.mixins.json` sets `defaultRequire: 1`, so every
  mixin is mandatory.
- **Reflection strings** in the Voxy and Tellus integrations.

## Known port work

- **`net.minecraft.resources.Identifier` → `ResourceLocation`** (22 references).
  Mechanical rename; `ResourceLocation.parse` exists in 1.21.1.
- **Chunk ticket API.** `ServerChunkCache.addTicketWithRadius(TicketType.FORCED, pos, 0)`
  and its `removeTicketWithRadius` counterpart are the 1.21.5+ API. In 1.21.1 the
  signature is generic and value-carrying:
  `addRegionTicket(TicketType<T>, ChunkPos, int radius, T value)`.
  Confirmed by `javap`. The add/remove pairing must stay balanced or chunks leak as
  permanently force-loaded.
- **`PalettedContainerFactory`** (4 references, client LOD receive path) does not exist
  in 1.21.1. Hand-construct `PalettedContainer` for block states and biomes using the
  1.21.1 constructors with `Strategy.SECTION_STATES` / `SECTION_BIOMES`. Highest-effort
  item in the port.
- **`getMinSectionY()` → `getMinSection()`** (5 references, including
  `TellusIntegration.java:270`).
- **`ResourceKey.identifier()` → `location()`** (1 reference, found during the compile loop).
- **`MinecraftServerAccess` deleted.** Found during the mixin audit, not the compile loop —
  this one would have been a world-load crash, not a compile error. `MinecraftServer.emptyTicks`
  does not exist in 1.21.1; `javap` confirms no `empty*` member on `MinecraftServer`,
  `IntegratedServer` or `DedicatedServer`. With `defaultRequire: 1` the mixin would have hard-failed
  at apply time. Upstream calls `setEmptyTicks(0)` in `cleanupTask` to stop an empty server idling
  during background generation; 1.21.1 has no such auto-pause counter, so the call is dropped and
  the omission is behaviourally inert. This is the **only** behavioural difference from upstream.
- **`fabric.mod.json`** — `minecraft` dependency to `~1.21.1`.
- **`gradlew`** — restored the executable bit, which upstream had not set.

## Components requiring no change

**Voxy integration.** Its reflection targets were diffed against the local
`voxy-mc_1211` source (Voxy 0.2.14-alpha, Mojmap). All three match exactly:

- `me.cortex.voxy.common.world.service.VoxelIngestService.tryAutoIngestChunk(LevelChunk)`
- `VoxelIngestService.rawIngest(WorldIdentifier, LevelChunkSection, int, int, int, DataLayer, DataLayer)`
- `me.cortex.voxy.commonImpl.WorldIdentifier.of(Level)`

**Fabric API surface.** Every entrypoint the mod uses exists in 0.116.6+1.21.1,
including `HudRenderCallback` — deprecated in 1.21.6+ in favour of the HUD layer API,
but present and functional in 1.21.1. No event-layer rework.

**Tellus integration.** Tellus has no 1.21.1 build, so `TellusIntegration` and friends
will reflectively no-op at runtime. Their four classes are still ported, because they
reference real Minecraft APIs and must continue to compile.

## Rendering-state accessor fix

`VoxyIntegration`'s rendering-enabled probe was broken upstream and is repaired here.

The old chain looked for `isEnabled()` (which Voxy does not have) and fell back to reading the
`enabled` field via `unreflectGetter`, then invoked the handle with no receiver. `enabled` is an
*instance* field, so the handle's type is `(VoxyConfig)boolean` and a no-argument `invoke()` throws
`WrongMethodTypeException` — swallowed by an empty `catch (Throwable)`, making
`isVoxyRenderingEnabled()` unconditionally return `true`.

The rewritten resolver:

- **Prefers `isRenderingEnabled()`**, which is the accessor that actually answers the question. Voxy
  defines it as `isAvailable() && enabled && enableRendering`; the raw `enabled` field is only one of
  those three terms, so even a receiver-corrected field read would have been wrong.
- **Separates static from instance members**, keeping a singleton getter alongside an instance
  handle, and discarding an instance handle outright when no singleton can be located rather than
  leaving one that throws on every call.
- **Reads the singleton fresh on each query.** `VoxyConfig.CONFIG` is a non-final static that Voxy
  reassigns on config reload, so binding the handle once at init would pin a stale instance.

Verified by driving the real compiled `resolveEnabledAccessor` against stubs replicating Voxy's
shipped shape plus the field-only, static, absent-singleton and unrelated-class variants — 15 checks,
all passing, including config reload and the `enableRendering` term.

**Behavioural note:** this probe now genuinely works, so turning Voxy's rendering off will actually
suppress background generation. That is the upstream intent, but it is a live behaviour change from
what the mod previously did on any version, where generation never got suppressed.

## Verification

- `./gradlew build` green: compilation, mixin annotation processor, and jar packaging.
- `javap` audit of all six mixins against the 1.21.1 jar:
  `ChunkMap.tick(BooleanSupplier)`, `ChunkMap.readChunk(ChunkPos)`,
  `MinecraftServer.emptyTicks`, `ServerChunkCache.getChunkFutureMainThread`,
  `ServerChunkCache.runDistanceManagerUpdates`, `ServerLevel.entityManager`,
  `ServerLevel.sendBlockUpdated`.
- Headless `./gradlew runServer` smoke test to confirm mixins actually apply — the
  difference between "it compiles" and "it loads".
- A `runClient` test plan handed back for manual verification of generation throughput,
  Voxy ingest, and the debug HUD.

### Verification results (2026-07-31)

`./gradlew build` green; `Voxy World Gen V2-1.21.1-2.2.4.jar` produced. All mixin targets
audited against the exact Mojmap jar javac compiles with; the ticket-level formula was checked
at the bytecode level (`ChunkLevel.byStatus(FULL) - radius`, identical to 1.21.11) rather than
from memory. Headless `runServer` on a 1.21.1 dedicated server started clean — all five
remaining mixins applied, and the mod logged `voxy world gen initialized`.

**What the smoke test did not cover.** No player ever joined, and the worker loop idles when
the player list is empty. So chunk generation, ticket add/remove, Voxy ingest, and the LOD
network path were never exercised — those need the `runClient` plan below.
